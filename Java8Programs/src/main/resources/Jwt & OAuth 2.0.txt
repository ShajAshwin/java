JWT AUTHENTICATION FLOW

JWT TOKEN STRUCTURE:

  +──────────────────────+   .   +──────────────────────+   .   +──────────────────────+
  │       HEADER         │       │       PAYLOAD        │       │      SIGNATURE       │
  │──────────────────────│       │──────────────────────│       │──────────────────────│
  │  Algorithm type      │       │  User data (JSON)    │       │  Hash of:            │
  │  e.g. HS256          │       │  userId, role, exp   │       │  Header + Payload    │
  │  Token type: JWT     │       │  + any custom claims │       │  + secret key        │
  +──────────────────────+       +──────────────────────+       +──────────────────────+

STEP 1:

             POST /login
  +--------+  ──────────────>  +──────────────────────+  ──────────────>  +─────────────────────+
  │        │                   │   Auth Controller    │                   │   Token Generator   │
  │ Client │                   │ Validates credentials│                   │  Signs + sets expiry│
  │        │                   +──────────────────────+                   +─────────────────────+
  +--------+                                                                     |
      ^                                                                          |
      │                    JWT token returned                                    |
      └──────────────────────────────────────────────────────────────────────────|
Token format:  Base64(Header) . Base64(Payload) . Signature

SUMMARY:
  1. Client sends credentials  -->  POST /login
  2. Auth Controller validates credentials
  3. Token Generator creates JWT  (Header . Payload . Signature)  with expiry
  4. JWT token returned to client
  5. Client attaches token to every request  -->  Authorization: Bearer <token>
  6. JWT Filter intercepts the request
       ├── Public route (e.g. /swagger-ui)  -->  Allow through directly
       └── Protected route                  -->  Validate token
             ├── Valid & not expired        -->  Forward to Controller  -->  200 OK
             └── Invalid / expired          -->  401 Unauthorized

OAuth 2.0:

Steps 1–5 (front-channel — browser visible):

User clicks "Login with Google" on your app
Your app redirects to Google's /authorize with the scope it needs
Google shows the consent screen
User approves → Google redirects back with a short-lived auth code

Steps 6–7 (back-channel — server to server, user can't see this):

Your backend secretly exchanges the auth code + client secret for tokens
Google returns an access token (JWT!) and a refresh token
This is done server-side so the client secret is never exposed to the browser

Steps 8–10 (using the token — same as your JWT flow!):

Your app calls the API with Authorization: Bearer <token>
Resource server validates the JWT signature
Returns the protected data

What problem does OAuth solve?
JWT handles your own app's login.
OAuth handles "Login with Google / GitHub / Facebook" — i.e. letting a third-party app access your data without giving them your password.
Without OAuth:  "Give Gmail your Facebook password to import contacts"  ❌
With OAuth:     "Facebook asks YOU to approve Gmail's access"           ✅

What is OAuth 2.0 and what problem it solves

What is an Authorization Code

🟡 Level 2 — Grant Types (most important)

Authorization Code Flow ← most common, learn this first
Client Credentials Flow ← for machine-to-machine (no user)
Implicit Flow ← deprecated, but asked in interviews
Resource Owner Password Flow ← also deprecated

🔴 Level 3 — Advanced

PKCE (Proof Key for Code Exchange) — secure OAuth for mobile/SPAs
OpenID Connect (OIDC) — OAuth + identity layer (adds who you are, not just access)
Token introspection & revocation
Difference between OAuth 2.0 and OAuth 2.1


How JWT fits into OAuth
OAuth handles:   WHO grants access and WHAT is allowed (scopes)
JWT is used as:  The actual Access Token that carries this info

Authorization Server  ──►  issues a JWT Access Token
Resource Server       ──►  validates that JWT (just like your JWT filter!)
